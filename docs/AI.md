# AI 활용 기록

이 프로젝트를 진행하면서 AI(Claude)를 활용했다. 아래는 주요 항목별로 AI를 어떻게 활용했는지에 대한 정리한 기록이다.

## Domain 순수성 vs WebFlux

- 배경: 통합검색에서 공급사 A/B를 병렬로 호출하는 방법을 고민하던 중, 처음엔 가상 스레드(virtual thread) vs `CompletableFuture`로 구현했다가, WebClient 자체가 non-blocking이라 가상스레드의 이점이 크지 않고, CompletableFuture로 변환하는 것도 불필요한 추상화가 추가 의문이 들어 AI에게 트레이드오프를 물었다.
- AI가 제시한 것: `Mono`/`Flux`를 안 끊고 끝까지 살리는 방식과, 그 경우 domain/application이 `Mono`/`Flux` 타입에 의존하게 돼 지금까지 지켜온 "도메인 순수성" 원칙과 충돌한다는 점을 설명. 이를 해결하기 위한 절충안(`SupplierSearchPort`는 평범한 동기 인터페이스로 유지하고, 리액티브 체인은 `adapter-out-supplier` 내부에만 가두는 구조)을 설계안으로 제시받았다.
- 직접 판단한 것: 이 절충안을 채택할지, 그리고 어느 선까지 "순수성을 포기해도 괜찮은지"의 기준은 직접 정했다. 

## 도메인 매핑 설계

- 배경: 초기 도메인 모델(Hotel/RoomType/DailyRate 등)을 직접 초안으로 작성했는데, 가장 큰 고민은 "공급사 응답 중 어떤 걸 버리고 어떤 걸 남길지"였다.
- AI가 지적한 것: `StayOffer`가 무엇을 표현하는지 불명확한 점, 매핑 테이블을 엔티티로 저장할지 여부, `breakfastIncluded`/`currency`를 방의 속성으로 둘지 요금의 속성으로 둘지 등을 질문 형태로 짚어줬다.
- 직접 판단한 것: "숙소 목록(자주 안 바뀜)은 매핑만 영속하고, 요금/재고(매번 바뀜)는 저장하지 않는다"는 원칙, `breakfastIncluded`를 `StayOffer`(요금 쪽)에 두는 결정 등. AI는 후보안과 각 안의 트레이드오프를 정리해주는 역할이었다.

## 재시도(Retry)

- AI에게 질문한 것: resilience4j `@Retry`/`@CircuitBreaker`를 어디에 붙여야 스프링 AOP 프록시가 정상 동작하는지(개별 Supplier Client의 인터페이스 구현 메서드에 붙여야 하는 이유), Retry와 CircuitBreaker의 데코레이터 순서를 어떻게 잡아야 하는지에 대한 설계 및 부하테스트 스크립트 작성.
- 직접 판단하고 검증한 것: "무엇을 재시도하고 무엇을 하지 않을지"(HTTP 4xx·비즈니스 실패는 재시도 안 함, 5xx·네트워크 오류만 재시도). `max-attempts=3`이라는 최종 값은 감으로 정하지 않고, mock-supplier에 "flaky" 모드를 추가해 실제로 1/2/3/5회를 놓고 성공률·지연시간을 실측 비교한 뒤 결정 

## 병렬성

- AI에게 질문한 것: `Flux.flatMap`으로 공급사를 동시 호출하는 코드 구현, 이게 실제로 병렬로 도는지 검증할 방법(mock-supplier에 인위적 지연을 걸고 순차/병렬 예상치와 비교) 설계 및 스크립트 작성.
- 직접 판단한 것: 동시성 자체를 늘리는 부하 테스트를 요청했고, 그 결과(VUs=200에서 실패율 발생)를 보고 "이거 어떻게 해결하지"라고 원인 규명을 요청. AI가 macOS 커널의 listen backlog 문제라고 규명하고 `ramping-vus`로 재현 실험을 제안했는데, 최종적으로 "이건 애플리케이션 결함이 아니라 테스트 방식의 문제"라는 결론

## 캐시

- AI에게 질문한 것: 숙소 매핑 캐시(`hotelMappingsBySupplier`)와 요금/재고 캐시(`availabilityCache`)의 실제 구현(Caffeine `@Cacheable`, `AsyncCache`), 캐시 무효화를 `@CacheEvict` 대신 코드로 직접 처리해야 하는 이유 설명, TTL 검증용 부하 테스트 스크립트 작성.
- 직접 판단하고 지적한 것: "지금 테스트로는 TTL이 길수록 히트율만 계속 오르는 거 아니냐"는 지적을 직접 제기해서, 히트율만으로는 TTL의 적정성을 검증할 수 없고(staleness 비용을 안 재고 있다는) 방법론적 한계를 짚어냈다. 이후 TTL 45초를 "수확체감 지점"으로 확정한 것도 반복 실험 결과를 직접 검토하고 판단한 결과다.

## 캐시 테스트는 python(bash) 스크립트로, 나머지(재시도/병렬성)는 k6로 한 이유

- 캐시 TTL 검증(`scripts/cache-load-test.sh`)은 처음 캐시 기능을 붙인 직후에 급하게 필요해서, 이미 쓰던 `curl` + `python3`(집계용)만으로 빠르게 짰다. 이땐 k6를 쓰자는 논의가 없었다.
- 이후 재시도 횟수 검증을 요청하는 과정에서 "이것도 스크립트로 검증할까"라는 이야기가 나왔고, bash 스크립트의 동시성 처리 방식에서 실제로 버그(`wait`가 백그라운드 서버 프로세스까지 같이 기다려 무한 대기)가 발생한 걸 계기로 "k6 있으니까 k6로 바꿔줘"라고 직접 지시해서 재시도·병렬성·동시성 테스트부터는 k6로 전환했다.
- 즉 두 방식이 공존하는 건 처음부터 의도한 설계가 아니라, 프로젝트가 진행되면서 "더 검증된 도구가 있으면 바꾼다"는 실용적 판단을 그때그때 반영한 결과다. 캐시 테스트를 k6로 다시 옮기지는 않았다 — 이미 동작이 검증됐고 재작성할 실익이 없다고 판단했기 때문.

## 테스트 스크립트

- AI에게 질문한 것: `SearchStayServiceTest`/`SearchCriteriaTest`/`MoneyTest` 같은 단위 테스트 코드 작성, `scripts/*.sh` + `*.js` 부하 테스트 스크립트 작성과 실행, 결과 해석.
- 직접 판단한 것: 테스트 메서드명을 한글로 바꾸도록 지시했고, 어떤 경로(성공/실패/엣지케이스)를 검증할지의 우선순위, 부하 테스트 파라미터(플래키 확률, 반복 횟수, 동시성 수준)와 그 결과를 근거로 무엇을 결론 내릴지는 직접 정했다. 스크립트 실행 중 발견된 버그(k6 태그 카디널리티 경고, 오프셋 배율이 너무 커서 날짜 파싱이 깨지는 문제 등)는 AI가 원인을 찾아 수정했다.
